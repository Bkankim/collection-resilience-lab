# collection-resilience-lab

수집 안정화 실험실. 차단하는 서버와 수집 워커를 함께 만들어 차단 → 감지 → 대응 → 회복을 재현 가능하게 측정합니다.

> 작업 중입니다. 2026-09-22 시작.

## 왜 이렇게 만들었나

외부 사이트를 대상으로 수집 안정화를 실험하면 약관과 법을 건드립니다. 그래서 **수집 대상 서버를 직접 만들었습니다.** 레이트리밋, IP 차단, 세션 만료를 스위치로 켜고 끌 수 있으니 대응 로직을 같은 조건에서 반복 측정할 수 있습니다.

차단하는 쪽 설계는 보안관제에서 하던 일입니다. 임계치를 정하고 액션을 걸고 오탐을 줄이는 작업을, 이번에는 반대편에서 다시 해봤습니다.

## 구조

| 디렉터리 | 역할 |
|---|---|
| `target/` | 수집 대상 서버. 로그인, 2차 인증, 거래내역 조회. 차단 시나리오를 스위치로 토글 |
| `collector/client/` | 수집 클라이언트. 세션 관리, 응답 파싱, 에러 분류 |
| `collector/api/` | 수집 요청 API. 요청을 받아 큐에 넣고 작업 ID를 즉시 반환 |
| `collector/worker/` | 큐 소비자. 재시도, 프록시 전환, 재인증, DLQ |
| `scripts/` | 시나리오 실행과 결과표 생성 |

## 실행

지금 동작하는 것은 수집 대상 서버까지입니다.

```bash
pnpm install
pnpm dev:target          # http://localhost:8080
pnpm test                # 42개 (대상 서버 통합 테스트 33개 포함)
```

띄운 뒤 주고받은 기록은 [`docs/evidence/d1-target-server.md`](docs/evidence/d1-target-server.md)에 있습니다.

`docker compose up -d`와 `pnpm scenario`는 아직 동작하지 않습니다. 워커와 프록시 컨테이너, 시나리오 러너가 들어온 뒤에 이 자리에 적겠습니다.

W 창(초), N 창 안 허용 요청, M 차단까지 429 누적(기간 없음), T 차단 시간(초), S 세션 수명(초). 켠 스위치는 (2) rateLimit,
(3) rateLimit + ipBlock, (4) sessionExpiry입니다. 네 시나리오 모두 완료 200, 실패 0, DLQ 0입니다.

- **성공률** = 완료 작업 수 / 200.
- **회복 시간** = 워커가 받은 첫 실패 응답(비 2xx)부터, 그 뒤 끝난 순서로 작업 10건이 연달아 완료된 시각까지. 작업이 실패로
  끝난 것을 세지 않는 이유는 이 설계가 속도 제한·차단에서 작업을 버리지 않아 작업 단위 실패가 거의 없기 때문입니다.
- **처리량** = 완료 작업 수 / 첫 작업을 넣기 직전부터 마지막 작업이 끝날 때까지의 초.

**회복 시간은 실패가 멈춘 시점을 재지 않습니다.** 이 설계에서는 작업이 실패로 끝나지 않으므로, 회복 시간은 사실상 "첫 실패 응답 뒤
작업 10건이 끝나는 데 걸린 시간"이고 10/처리량과 비슷합니다(13.78 대 14.01, 14.37 대 17.06, 9.18 대 10.46). 실패 응답은 세 시나리오
모두 실행 거의 끝까지 이어졌습니다(실패 응답 구간이 소요 시간보다 2.6~5.7초 짧을 뿐입니다). 회복 시간의 기준점은 속도 제한과 출발지 차단
모두 첫 429 `/login`이고, 세션 만료는 첫 401 `/transactions`입니다.

기대와 맞춰 보면 이렇습니다.

- 속도 제한: 기대대로 처리량이 떨어지고(1.24 -> 0.71건/초) 작업 실패는 0건입니다. 429 200번마다 큐를 멈추고 로그인부터 다시 해 이어 받았습니다.
- 출발지 차단: 전환(69번) 뒤 이어 받아 작업은 전부 끝났지만, "이후 회복"은 한 번으로 끝나지 않았습니다. M에 기간이 없고
  두 워커가 같은 출발지로 몰려 두 출발지가 번갈아 막혔고(모두 막힘 81번), 처리량은 속도 제한만 켰을 때보다 낮습니다(0.59).
  기대와 다른 점입니다. 다른 워커의 속도 제한으로 큐가 멈춰 있어 전환을 미룬 것(`origin-rotation-held`)은 6번입니다.
- 세션 만료: 작업마다 한 번씩 만료(401 200번)되고 재로그인(로그인 402번 = 작업 200 + 재로그인 200 + OTP 거부 뒤 재시도 2)으로 이어 받았습니다.

속도 제한과 세션 만료의 403 2번씩은 차단이 아니라 2차 인증 코드 거부(OTP_REJECTED)였습니다. 넷 다 분 경계 직후(20:24:00.139,
20:37:00.025~.026 UTC)였고, 대상 서버의 TOTP 검증은 시각 허용 오차가 0(otplib `verifySync` 기본값)이라, 30초 경계 직전에 만든 코드가
150ms 지연 뒤 경계를 넘어 닿은 것으로 봅니다(시각으로 본 추정, 따로 재현하지 않았습니다). 워커는 TRANSIENT로 한 번 재시도해 완료했습니다.

## 한계

- 수집 대상은 실제 금융기관이 아니라 이 리포가 만든 모사 서버입니다.
- 재현한 차단은 3종뿐이고, 실제 환경은 이보다 복잡합니다.
- 공동인증서 기반 전자서명은 구현하지 않았습니다. 2차 인증은 TOTP로 단순화했습니다.
- **세션 만료와 자격증명 거부를 응답 헤더로 구분합니다.** 둘 다 401이지만 대응이 정반대(재인증 vs 즉시 중단)라서 나눌 근거가 필요했습니다. 실제 기관은 이 구분을 본문 메시지로만 주는 경우가 많고, 그러면 수집하는 쪽이 문구에 의존하게 됩니다. 문구는 공지 없이 바뀝니다.
- **2차 인증 실패는 계정 잠금 대상이 아닙니다.** 양쪽 시계가 어긋나기만 해도 TOTP는 틀리므로 비밀번호 오류와 같이 세지 않았습니다. 실제로는 OTP 오류도 누적해 잠그는 기관이 있습니다.
- **세션 쿠키에 `Secure`를 붙이지 않았습니다.** 실험실이 평문 HTTP로 뜨기 때문이고, 붙이면 브라우저가 쿠키를 버려서 동작하지 않는 방어가 됩니다.
- **출발지는 소켓 주소로만 판정합니다.** `X-Forwarded-For`를 믿으면 헤더 한 줄로 차단이 풀립니다. 대신 출발지를 실제로 나누려면 프록시 컨테이너를 거쳐야 하고, 호스트에서 포트로 바로 들어오면 전부 같은 출발지로 보입니다.
- **관리 API(`/admin/*`)에 인증이 없고 서버가 `0.0.0.0`에 바인드합니다.** 컨테이너에서 띄우려면 필요하지만, 노트북에서 그냥 띄우면 같은 망의 누구나 차단 스위치를 끄고 상태를 초기화할 수 있습니다. 실험 장비라서 그대로 뒀습니다.
- **출발지 차단은 속도 제한에 종속입니다.** 차단 조건이 "429를 M회 누적"이라, 속도 제한을 끄면 출발지 차단도 발동하지 않습니다. 그리고 M에는 기간이 없습니다(W와 달리 창이 없습니다).
- **재인증 동시성 제어는 범위 밖입니다.** 같은 로그인 ID의 작업이 동시에 돌면 각자 따로 로그인합니다. 대상 서버에 "로그인 하나에 세션 하나" 정책이 없어서 한 워커의 재인증이 다른 워커의 세션을 죽이는 라이브락이 생기지 않기 때문입니다. 단일 세션을 강제하는 기관을 대상으로 하면 로그인 ID별 잠금이 필요합니다.
- **AUTH_FAILED 차단기는 사람이 풉니다.** 한 작업이 AUTH_FAILED를 받으면 같은 로그인 ID의 다른 작업은 로그인을 보내지 않고 바로 실패합니다(비밀번호 오류가 쌓여 계정이 잠기는 것을 막습니다). 1차 인증에서 분류기가 모르는 응답(구분 헤더 없는 401, 423 등, UNKNOWN)이 와도 같은 이유로 막습니다. 차단에는 만료가 없습니다. 풀려면 자격증명을 고친 뒤 Redis의 `authblock:{큐}:{로그인 ID}` 키를 지우고, **그 사이 실패한 작업도 다시 돌리거나(`job.retry()`) 지워야 합니다.** 실패 작업은 보존되고 같은 요청은 같은 작업 ID라서, 키만 지우고 같은 요청을 다시 넣으면 새로 돌지 않고 실패로 남습니다. 차단을 보기 전에 이미 출발한 작업은 각자 한 번씩 로그인합니다.
- **속도 제한·차단 중 작업은 받은 페이지부터 이어받고, 로그인은 매번 다시 합니다(#19).** 페이지마다 결과와 다음 페이지 번호를 남기므로 요청 수가 대상 서버의 창(N)보다 많은 작업도 주기마다 나아가 끝납니다. 큐 정지(주기)를 3번(`WORKER_NO_PROGRESS_CYCLES`) 연달아 거치는 동안 큐의 어느 작업도 페이지를 받거나 완료하지 못하면, 그 주기에 제한을 받은 작업은 DLQ에 `NO_PROGRESS`로 갑니다. 창이 동시에 출발하는 워커들의 로그인 비용 이하인 경우입니다. 직전 정지가 끝나고 60초 넘게 조용했다가 온 제한은 연속으로 치지 않고 1부터 셉니다. 반대로 NO_PROGRESS 뒤 60초 안에는 연속이 이어지므로, 회복된 큐의 첫 주기에서 다른 워커의 진행 세기보다 429 세기가 먼저 돌면(한 번 왕복 차이) 그 작업은 바로 DLQ로 갑니다. 규칙 전체는 `collector/worker/process.ts`의 `DEFAULT_NO_PROGRESS_CYCLES` 주석에 있습니다. 이 상한은 공정성을 다루지 않아서, 큐가 나아가는 동안 한 작업이 창 경쟁에서 계속 지면 그 작업은 늦어집니다(실측 여섯·여덟 주기, `docs/evidence/d3-resume.md` 4절·6-2절). 워커 여러 개가 제한이 풀리는 순간 같이 출발해 서로의 창을 먹는 것은 그대로이고, 이것은 워커 limiter를 대상 서버 임계값에 맞춰 조이면 풀립니다. 다만 429가 한 번 나면 BullMQ가 limiter 창을 Retry-After로 덮어써서 그 주기는 Retry-After 간격이 됩니다(`docs/evidence/d2-pipeline.md` 3절, `docs/TROUBLESHOOTING.md` 4번).
- **이어받기는 페이지 번호로 합니다(#19).** 다시 시작하면 체크포인트의 페이지부터 받습니다. 실제 대상이 기다리는 동안 앞 페이지의 행을 지우거나 순서를 바꾸면 페이지 경계가 밀려, 행 하나를 영영 받지 못하거나 두 번 받습니다(두 번은 seq 필드라 늘지 않습니다). 거래 번호(seq)로 이어받으려면 대상 서버가 "이 seq 다음부터" 조회를 지원해야 하는데, 이 실험실의 원장은 바뀌지 않아 그 경우가 생기지 않습니다. 또 체크포인트 쓰기는 BullMQ 잠금을 확인하지 않아서, 잠금을 잃은 채 늦게 깨어난 워커가 체크포인트를 뒤로 덮을 수 있습니다. 행은 잃지 않고 요청과 진행 한 번이 더 나갈 뿐입니다. 막으려면 잠금 토큰으로 거르는 스크립트가 필요합니다.
- **실패한 작업의 부분 결과는 남깁니다.** 워커는 페이지마다 결과 해시(`results:{큐}:{작업 ID}`)에 쓰므로 실패 작업에도 받은 만큼의 행이 있고, 다시 돌리면(`job.retry()`) 그 체크포인트부터 이어받는 데 씁니다. API는 완료된 작업만 결과를 보여 줍니다. 작업 상태를 보지 않고 결과 해시를 직접 읽지 마십시오. 작업을 지울 때는 결과 해시도 같이 지웁니다(만료가 없어 남으면 계속 쌓입니다). 결과 해시가 체크포인트보다 적으면(사람이 지운 경우 등) 워커는 1페이지부터 다시 받습니다.
- **출발지는 차단(IP_BLOCKED)일 때만 바꾸고, 속도 제한(429)에는 바꾸지 않습니다(#14).** 워커에 `WORKER_PROXIES`로 프록시를 주면(compose의 `proxy-a`·`proxy-b`, 대상 서버는 `TARGET_ORIGIN=http://target:8080`), 403 IP_BLOCKED를 받은 출발지를 대상 서버가 준 Retry-After가 끝날 때까지 후보에서 빼고 막히지 않은 다음 출발지(목록 순서)로 **로그인부터 다시 해** 받은 페이지부터 이어 받습니다. 이때는 큐를 멈추지 않고 진행 기반 상한의 주기로도 세지 않고 시도 횟수도 쓰지 않습니다. 429를 출발지를 바꿔 피하는 것은 상대가 정한 한도를 우회하는 것이라, 429는 지금처럼 큐 전체를 멈춥니다. 출발지가 모두 막히면 가장 빨리 풀리는 출발지까지 큐 전체를 멈추고, DLQ로는 진행 기반 상한(NO_PROGRESS)으로만 갑니다. 고를 때 출발지별 성공·실패 수는 쓰지 않고 로그(`origin-result`)로만 남깁니다. 프록시를 주지 않으면 출발지가 하나라 D2처럼 Retry-After만큼 기다립니다. 출발지를 실제로 가르려면 대상 서버도 프록시와 같은 compose 네트워크에 있어야 합니다(호스트에서 띄우면 두 프록시가 같은 주소로 보입니다). 실측은 [`docs/evidence/d3-origin.md`](docs/evidence/d3-origin.md)에 있습니다.
- **출발지 차단 상태는 워커 프로세스마다 따로 듭니다.** 워커끼리 나누지 않아서, 한 워커가 겪은 차단을 다른 워커는 모르고 그 출발지로 한 번 보내 403을 받은 뒤에야 뺍니다(워커마다 차단을 한 번씩 겪습니다). 워커들은 모두 목록의 첫 출발지부터 쓰므로 같은 출발지의 창을 같이 먹고, 창이 같이 출발하는 워커들의 로그인 비용 이하면 출발지가 둘이어도 NO_PROGRESS로 끝납니다(실측 N=4, 워커 2개).
- **출발지를 바꾸면 세션을 새로 만드는 것은 가정입니다.** 세션을 발급 출발지에 묶는 기관을 가정해 전환마다 로그인(2요청)을 다시 보냅니다. 이 실험실의 대상 서버는 묶지 않아서, 한 출발지에서 받은 세션이 다른 출발지에서도 통합니다.
